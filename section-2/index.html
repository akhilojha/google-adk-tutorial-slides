THEORY  ·  LLM vs Agent — what's the difference?

What Is an Agent?

A plain LLM
You send a prompt. The model returns text. One round trip — done. It has no memory of prior messages, no ability to fetch data, and no way to take actions in the world.
user → LLM → text
text in · text out · no loop · no tools
⚠️
Knowledge is frozen at training time
Ask an LLM "What's the weather in Tokyo right now?" — it cannot know. Its weights were fixed months ago. It can only describe what it would do, not actually do it.
An agent
An agent is an LLM wrapped in a loop. On each turn it can observe the conversation, decide to call a tool, receive the result, and loop again — until it has everything it needs to answer.
user →
observe → think → act (tool)
← result → think → act (tool)
← result → final answer
✅
The mental model
The LLM is the brain — it reasons and decides. Tools are the hands — they reach outside into the real world. An agent is the combination of both.

THEORY  ·  What gives an agent its power?

What Are Tools & Why Agents Need Them

Without tools
Frozen knowledge
An LLM's weights are fixed at training time. Ask it today's temperature in Tokyo — it cannot know. That fact didn't exist when it was trained.
No side-effects
A plain LLM produces text only. It cannot fetch a URL, read a database, or call an API. It can only describe doing those things.
⚠️
Everything useful lives outside the model
Weather, country facts, prices, tickets — none of it is in the weights. All of it needs a network call.
With tools
Real-time data
A tool is a plain Java method. It can call any API, read any database, run any code. The result comes back as data the LLM reasons over.
Real-world actions
Tools can have side-effects — send a Slack message, create a ticket, restart a service. The LLM decides when. Your code executes it.
Composability
One agent can have many tools. The LLM reads all their descriptions and picks the right one per turn — or calls several. You write zero routing logic.

STEP 2  ·  Simplest tool first — one API call, no chaining

Add getCountryInfo

java TripPlannerAgent.java 
@Schema(description = "Get key travel facts about a country")
public static JsonNode getCountryInfo(
    @Schema(name = "country", description = "Country name, e.g. Japan") String country
) throws Exception {
    return fetch(
        "https://restcountries.com/v3.1/name/"
        + country.replace(" ", "%20")
        + "?fields=name,capital,currencies,languages,timezones,population"
    ).get(0);
}

private static JsonNode fetch(String url) throws Exception {
    HttpRequest req = HttpRequest.newBuilder(URI.create(url)).GET().build();
    String body = HttpClient.newHttpClient().send(req, HttpResponse.BodyHandlers.ofString()).body();
    return new ObjectMapper().readTree(body);
}
Wire it to the agent
.tools(
    FunctionTool.create(
        TripPlannerAgent.class,
        "getCountryInfo")
)
One tool — agent can now answer questions about any country.
💡
fetch() is your HTTP helper
One method — builds a GET request, sends it, parses the body as JSON. All three tools will reuse it.
⚠️
Notice the @Schema annotations
These descriptions are what the LLM reads when deciding to call this tool. Next slide explains exactly why they matter.
IMPORTANT  ·  Without this, FunctionTool's reflection breaks silently

The @Schema Annotation

The description you write here is what the LLM reads when deciding whether and how to call your tool.

What the LLM actually sees (JSON Schema)
json sent to the LLM in every request 
{
  "name": "getCountryInfo",
  "description": "Get key travel facts about a country",
  "parameters": {
    "type": "object",
    "properties": {
      "country": {
        "type": "string",
        "description": "Country name, e.g. Japan"
      }
    },
    "required": ["country"]
  }
}
Fallback — compiler flag  (names only, no descriptions)
xml pom.xml — already set in this project 
<compilerArgs>
  <arg>-parameters</arg>
</compilerArgs>
💡
Description quality = call quality
The LLM reads these when deciding whether to call the tool and what to pass.

"Country name" is fine. "Country name, e.g. Japan" is better — the example guides the model to pass the right format.
⚠️
No annotation = silent failure
Without @Schema and without -parameters, javac names params arg0, arg1…

ADK logs a warning but doesn't throw. The LLM either skips the tool or passes garbage arguments.

STEP 3  ·  Two tools that chain — the LLM calls them in order

Add getCityCoordinates & getWeather

java TripPlannerAgent.java 
@Schema(description = "Get the latitude and longitude for a city")
public static JsonNode getCityCoordinates(
    @Schema(name = "city", description = "City name, e.g. Tokyo") String city
) throws Exception {
    return fetch(
        "https://geocoding-api.open-meteo.com/v1/search?name="
        + city.replace(" ", "+") + "&count=1&language=en&format=json"
    ).path("results").get(0);
}

@Schema(description = "Get current weather for a location given its coordinates")
public static JsonNode getWeather(
    @Schema(name = "latitude",  description = "Latitude, e.g. 35.6895")  double latitude,
    @Schema(name = "longitude", description = "Longitude, e.g. 139.6917") double longitude
) throws Exception {
    return fetch(String.format(
        "https://api.open-meteo.com/v1/forecast"
        + "?latitude=%.4f&longitude=%.4f"
        + "&current=temperature_2m,relative_humidity_2m,wind_speed_10m",
        latitude, longitude
    )).path("current");
}

BEHIND THE SCENES  ·  What actually happens when you send a message

How the LLM Picks a Tool

1
ADK attaches every tool's schema to the request
jsonsent to the LLM alongside your message
[
  { "name": "getCountryInfo",    "description": "Get key travel facts about a country" },
  { "name": "getCityCoordinates", "description": "Get the latitude and longitude for a city" },
  { "name": "getWeather",         "description": "Get current weather given coordinates" }
]
2
LLM reasons over the descriptions — no if/else in your code
"User wants weather and travel info for Tokyo.
getCountryInfo → travel facts ✓   getCityCoordinates → I need lat/lon first ✓   getWeather → needs lat/lon, call after ✓"
3
LLM responds with a tool call — not text
jsonLLM output — ADK executes this, not you
{ "name": "getCityCoordinates", "args": { "city": "Tokyo" } }
ADK calls your Java method, appends the result to the session, then calls the LLM again — until finalResponse().
💡
The LLM never runs your code
It only produces a JSON object naming the tool and its arguments. ADK reads that JSON, calls the matching Java method, and feeds the result back. The LLM sees results as text — it never touches the JVM.
⚠️
Description quality = decision quality
With three tools in the list the LLM picks purely based on what you wrote in @Schema. Vague description → wrong tool called. Good description → correct chain every time.
✅
You write zero routing logic
No switch statements, no if/else on intent. The model reads the menu, decides what to order, and ADK serves it. Your job is writing the methods and their descriptions.
FULL CODE  ·  The complete class — run this

TripPlannerAgent.java

java src/main/java/com/thebaselinedev/llms/TripPlannerAgent.java 
package com.thebaselinedev.llms;

import com.google.adk.agents.LlmAgent;
import com.google.adk.models.LlmRegistry;
import com.google.adk.tools.Annotations.Schema;
import com.google.adk.tools.FunctionTool;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class TripPlannerAgent {

    private static final String MODEL_NAME = "qwen/qwen3.5-9b";
    private static HttpClient HTTP = HttpClient.newHttpClient();

    static { LlmRegistry.registerLlm(MODEL_NAME, name -> new LocalLLM(MODEL_NAME)); }

    public static final LlmAgent ROOT_AGENT = LlmAgent.builder()
        .name("trip-planner-agent")
        .description("Helps users plan trips")
        .instruction("You are a helpful trip planning assistant.")
        .model(MODEL_NAME)
        .tools(
            FunctionTool.create(TripPlannerAgent.class, "getCountryInfo"),
            FunctionTool.create(TripPlannerAgent.class, "getCityCoordinates"),
            FunctionTool.create(TripPlannerAgent.class, "getWeather"))
        .build();

    @Schema(description = "Get key travel facts about a country")
    public static String getCountryInfo(
        @Schema(name="country", description="Country name, e.g. Japan") String country
    ) throws Exception {
        return fetch("https://restcountries.com/v3.1/name/"
            + country.replace(" ", "%20")
            + "?fields=name,capital,currencies,languages,timezones,population");
    }

    @Schema(description = "Get the latitude and longitude for a city")
    public static String getCityCoordinates(
        @Schema(name="city", description="City name, e.g. Tokyo") String city
    ) throws Exception {
        return fetch("https://geocoding-api.open-meteo.com/v1/search?name="
            + city.replace(" ", "+") + "&count=1&language=en&format=json");
    }

    @Schema(description = "Get current weather for a location given its coordinates")
    public static String getWeather(
        @Schema(name="latitude",  description="Latitude, e.g. 35.6895")  double latitude,
        @Schema(name="longitude", description="Longitude, e.g. 139.6917") double longitude
    ) throws Exception {
        return fetch(String.format(
            "https://api.open-meteo.com/v1/forecast"
            + "?latitude=%.4f&longitude=%.4f"
            + "&current=temperature_2m,relative_humidity_2m,wind_speed_10m",
            latitude, longitude));
    }

    private static String fetch(String url) throws Exception {
        HttpRequest req = HttpRequest.newBuilder(URI.create(url)).GET().build();
        return HTTP.send(req, HttpResponse.BodyHandlers.ofString()).body();
    }
}
BEHIND THE SCENES  ·  What just happened when you ran that?

What ADK Actually Runs

1
Message enters the session
ADK wraps the user message and appends it to session history.
2
ADK builds the LlmRequest
Packs: system prompt + full session history + JSON Schema for all three tools. The LLM now knows getCountryInfo, getCityCoordinates, and getWeather exist and what they take.
3
LLM returns a tool-call request, not text
The model decides it needs real data and responds with a JSON request for getCityCoordinates("Tokyo"). No answer yet — the LLM cannot call code itself; it just asks ADK to do it.
4
ADK dispatches, loop repeats
ADK executes getCityCoordinates and feeds the result back. The LLM responds with another tool-call request — getWeather(lat, lon). ADK runs it, feeds the result back again. The LLM then requests getCountryInfo("Japan"). ADK runs that too.
5
All results in session, LLM writes the answer
After all three tools have run, ADK calls the LLM one final time with all results in the session history. Now the LLM has live weather data and country facts — it returns plain text.
6
finalResponse() fires
"Tokyo is 17.6°C with 75% humidity. Japan uses JPY and runs on UTC+9…" — grounded in data fetched moments ago.
02  ·  Key Takeaways

What you learned

LLM vs Agent
An agent wraps an LLM with tools and a decision loop — so it can act, not just answer.
Tools are plain Java methods
Annotate with @Schema, register with FunctionTool.create(). ADK converts the method signature into a JSON Schema the LLM reads on every request.
@Schema descriptions drive calls
The LLM does intent matching against your descriptions — not if/else logic. Clear descriptions = correct calls. No annotation = silent failure.
Tool chaining is automatic
getCityCoordinates → getWeather are chained by the LLM because one's output is the other's input. You write zero routing or glue code.
Three real APIs, no keys
RestCountries, Open-Meteo geocoding, and Open-Meteo forecast are all free with no auth. Your tools return live data from the very first run.
ADK owns the loop
BaseLlmFlow runs the LLM → tool → LLM cycle. runAsync returns a Flowable<Event> — filter with finalResponse() to get the answer.
